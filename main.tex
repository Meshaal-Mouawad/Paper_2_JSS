\begin{abstract}[]

Software calculates key performance indicators (KPIs), but the documentation explaining those calculations may not accurately describe what the code does. Even when documentation links to the correct source code, its explanations may contain errors or omit conditions that affect the calculated result.

We evaluated this problem using LEAP (Literate Programming for Automated KPI Extraction), a research software tool that extracts KPI information from source code and publishes source-linked documentation in an Interactive Bluebook. For example, one generated KPI page presented a production-yield formula but omitted a condition under which the software returns zero.

We audited 28 generated KPI documentation pages using deterministic checking rules and assessments from three independent reviewers. The evaluation tested four candidate dimensions of documentation accuracy. Two received reproducible reviewer support: correct descriptions of source-code elements (Fleiss' $\kappa = 0.407$) and disclosure of conditions affecting calculations ($\kappa = 0.553$).

The automated source-role checker detected only 2 of 16 errors identified by reviewer majority (12.5\% recall). For condition disclosure, checker precision differed between two assessment criteria: 40\% when source visibility counted as disclosure and 100\% under the reader-facing criterion used by the checker. The latter result reflected agreement with that criterion, not independent proof of perfect detection.

The study demonstrated that linking documentation to source code does not guarantee an accurate explanation. It also identified specific documentation errors and limitations of the automated rules used to detect them.
\end{abstract}

\section{Research Questions and Method}

\begin{description}[leftmargin=1.2cm,style=nextline]
\item[RQ1] Which \mes{discrepancies between source evidence and published KPI explanations} are exposed in the full 28-dossier LEAP output, and which generator mechanisms explain the repeated manifestations?
\item[RQ2] Which \mes{discrepancies in published KPI knowledge} persist or vary across an earlier project state and alternative input configurations?

\subsection{\texorpdfstring{Automated Checking Rules}{Automated Checking Rules}}
\baj{Why are these rules sufficient? What inputs cause them to produce incorrect results?}
An automated checking rule is a specific comparison that a program applies to every eligible page. For example, when source code returns zero for non-positive feedstock, the checker looks for that same condition in the published safeguard explanation. It reports \emph{Fail} when the required information is missing, \emph{Pass} when the checked requirement is satisfied, or \emph{NA} when the rule does not apply. The checker performs these comparisons automatically; the independent human reviewers make their own judgments about the pages.

We implemented four such rules because the literature identified four candidate problems in published documentation (Table~\ref{tab:contract}). Each rule handles only the code and wording patterns specified below. A passing result therefore means that the particular check found no problem, rather than proving the entire explanation correct. A \emph{guard} is a code condition that changes what happens for an exceptional input; the Yield example's return-zero branch is one such condition. The reviewer comparison then measured what the automatic rules detected and missed.
\mes{The rules implemented specific checks motivated by the literature in Table~\ref{tab:contract}. Prepared controls tested whether each rule returned its specified decision. Comparison with independent reviewers tested how many of their findings it detected. For source roles, it detected only 2 of 16 reviewer-majority failures.}
\begin{enumerate}[leftmargin=*]
\item \textbf{Source-role accuracy.} Each part of a program has a function: a comment explains code, an executable statement performs an operation, and an output alias names a result. A documentation error occurs when the page gives one of these parts the wrong role. The checker reads a source excerpt alongside its generated Developer Lineage description. It flags specified errors, such as presenting a function's descriptive text (a \emph{docstring}) as executable code or treating a SQL \texttt{CAST} conversion type as the output name instead of the actual alias. Figure~\ref{fig:sql-source-role} illustrates the latter case.
\item \textbf{Executable-guard disclosure.} A displayed formula may omit a rule that the program applies to unusual inputs. In the Yield example, the program returns zero whenever feedstock is zero or negative; this behavior cannot be inferred from the ordinary ratio alone. This checking rule asks whether the written safeguard describes such an implemented condition and identifies the variable it applies to. Eligibility covers explicit zero or non-positive denominator \baj{Why is a negative denominator a problem? For zero checks, does it also include values that are close to zero? Preservation requires reader-facing safeguard text to communicate zero/non-positive handling and match the guarded variable to the denominator of the displayed formal formula (the equation printed in the dossier). A \texttt{<= 0} guard requires non-positive semantics; zero-only wording fails the rule.
\mes{A negative nonzero denominator is mathematically valid. The obligation here arises from the implemented branch: the Yield source returns zero when feedstock input is non-positive. Consequently, zero-only safeguard wording omits part of the implemented condition.}
\item \textbf{Representation-disagreement candidate.} A KPI may have two recorded calculations that give different answers, such as a declared business formula and an executable formula. Rather than silently presenting one as correct, the page can mark the difference for a person to review. For pages with an explicit conflict, mismatch, or inversion marker, this rule checks that the page retains \emph{Needs Review} status and an entry in the Review Queue, the list of items awaiting a decision. It verifies that an existing conflict is routed, not that the conflict was resolved. We separately measured reviewer agreement on the broader disagreement criterion.
\item \textbf{Review-authority candidate.} The status \emph{Needs Review} tells a reader that a calculation has not been cleared for use. Calling the same page "certified" could instead suggest approval. This rule looks for such contradictory certification wording on unresolved pages, including phrases such as ``Certified metric dossier'', ``certified calculation expression'', or ``Print Certified Dossier''. Reviewer agreement determined whether this criterion was retained.
\end{enumerate}
The condition rule covered the specified zero and non-positive branches. It did not check near-zero numerical tolerances or the input domains of square-root, logarithmic, or inverse-trigonometric functions; those require separate tests (Section~\ref{sec:study-limitations}).
The scripts produced the full guard inventory and line-level source-role findings. Table~\ref{tab:contract} records the literature basis of the four criteria.

\subsection{Evaluated checker and conformance tests}
Two different questions matter when evaluating a checker. First, does its program return the expected answers for examples deliberately constructed to test each rule? These are \emph{conformance tests}. Second, does it find the errors identified when people examine real generated pages? The first question tests implementation of the specified rule; the second tests how useful the rule is on the evaluated documentation. We report both results separately.

The archived development sequence began with a written audit procedure labeled R3 (revision three) \baj{does this mean rule 3?} \mes{(the third protocol revision)}, which specified deterministic source-role and condition-disclosure criteria. R4 \mes{(the fourth implementation revision)} separated the current LEAP audit, earlier and alternative-input analyses, and external-format checks. Later control testing exposed checker defects that were repaired before the reported results. The evaluated released rules are in \texttt{audit\_rules.py}, with the corrections documented in the R5.1 release protocol. These labels name successive versions of the study materials, rather than numbered checking rules. The final evaluated checker implements the later corrections documented in the R5.1 protocol; it should not be confused with the earlier R4-stage implementation. The results refer to this released implementation. The released checker compares published roles and names with their source counterparts, requires a nonempty displayed denominator, and rejects missing, heading-only, or contradictory safeguard descriptions. The conformance tests below exercise these requirements through prespecified control outcomes.

We tested the checker on examples for which we had written down the expected decision before running the program. Some examples deliberately changed a correct source name or removed a safeguard; the expected answer for those defects was Fail. Other examples retained correct descriptions and should return Pass. The first set contained 18 rule fixtures covering correct and incorrect source roles, missing or mismatched denominator information, omitted or contradictory safeguard text, conflict routing, certification wording, and applicability. A second set of 14 controls was derived from archived pages: five unchanged examples, eight deliberately substituted inputs, and one modified web page read again through the normal page-reading adapter. These changes tested whether the program responded to the specific error introduced, without treating those controlled examples as a representative sample of all documentation. We compared each returned decision with its expected label.
\baj{Reviews will be suspicious here – the test found no failures for any of the rules? This would be more convincing if failures are in areas that humans will catch, etc.}
Matching the predefined expected labels (the control oracle) includes returning Fail when a control is deliberately defective. Across the 32 controls, the expected outcomes comprise 19 Fail, 11 Pass, and two NA (not applicable) labels. These results establish conformance to the specified control cases. Independent comparison on the original dossiers reveals the coverage limitation: the source-role checker misses 14 of the 16 reviewer-majority failures.


\subsection{\texorpdfstring{Independent Review: Initial and Checklist-Based Phases}{Independent Review: Initial and Checklist-Based Phases}}
The prepared controls told us whether each checking rule behaved as programmed. They did not tell us whether independent readers would identify the same problems on actual KPI pages. We therefore collected reviewer judgments and compared the outcomes with the automatic checker. This separated two questions: whether reviewers applied an assessment criterion similarly and whether the programmed check detected the problems they reported.

Three independent reviewers, identified as R1, R2, and R3 in the results, evaluated the same 28 pages, identified as C01--C28. These reviewer identifiers are distinct from the protocol and checker version numbers described above. The packets excluded checker outputs, manuscript result tables, the organizer mapping key, and other reviewers' responses. In the first pass (Phase A), reviewers described any problems they noticed without marking the four named criteria. In the second pass (Phase B), they assessed each page using that checklist. The packet contained the instructions for both phases. Phase B recorded Pass, Fail, or NA with supporting evidence; NA meant that the criterion was judged inapplicable.

Each of the 28 pages was assessed against four criteria, producing 112 page--criterion combinations. Three ratings per combination produced 336 individual ratings. All 28 Phase-A case rows were returned by each reviewer. The original Phase-B responses contained 242 Pass/Fail ratings and 94 explicit NA ratings (28.0\%). The 94 NA entries appeared as blanks in an intermediate analysis export: 40 of 84 condition ratings and 54 of 84 disagreement ratings. Restoring those entries to NA reproduced all 336 original labels. We also calculated agreement on the cases for which all three reviewers supplied Pass or Fail, indicating common applicability.

A majority decision required at least two matching ratings for a page--criterion combination. One condition case had a three-way split, leaving 27 resolved cases for that comparison. The other three criteria had 28 resolved cases each. We calculated average pair agreement, the fraction of matching labels across reviewer pairs, and Fleiss' $\kappa$, an agreement measure adjusted for agreement expected from the label frequencies \citep{Fleiss1971}. We compared checker decisions with the reviewer-majority labels. Exact agreement required the same Pass, Fail, or NA decision. For the binary comparison, Fail was positive and Pass/NA was non-fail.

A true positive (TP) was a checker flag supported by the majority reference; a false positive (FP) was an unsupported flag. A false negative (FN) was a majority-reference failure missed by the checker; a true negative (TN) was a non-fail case under both. Precision was the fraction of checker flags supported by the reference, and recall was the fraction of reference failures flagged by the checker. Exact / n in the results tables reports identical three-state decisions out of the resolved comparisons. The separate condition-criterion comparison used the same 10 checker-eligible cases under each disclosure definition.

The organizer guidance specified three reviewers, Fleiss' kappa, majority-agreement reporting, and a later adjudication step. The reviewer-packet README instead recommended two reviewers and Cohen's kappa, also followed by adjudication. The reported analysis used the three returned forms, Fleiss' kappa, and the stated majority rule as the comparison reference. We preserved the individual ratings and documented the protocol difference in the supplement.

Phase B followed Phase A on the same cases. We compared the majority issue sets and inspected the five cases flagged only in Phase B to identify which criterion accounted for the difference.

\subsection{Verification and root-cause procedure}
After identifying a wrong explanation, we examined which part of the generator had produced it. This \emph{root-cause inspection} connected visible errors to the instructions in the program or page template that generated the text. One cause could appear repeatedly on several KPI pages.

The primary audit script checked the page count, SHA-256 file identities, review-status counts, source-role descriptions, guard conditions, conflict routing, and certification wording. Primary, historical, alternative-input, and external scripts used the same released rule library for applicable checks. The primary scanner identified ten eligible guard cases. The release verifier checked the expected control labels and both conformance-test sets before accepting the corpus summaries.

After identifying documentation errors, we inspected the archived generator code to trace their causes. We linked repeated errors to a common cause when the same code explained their occurrence across pages. The supplement retains the generator excerpts and file hashes used in this inspection.

\subsection{Root-cause localization}
LEAP creates its explanatory text using common rules and templates. If one rule misinterprets source code, the same mistake can appear on several published pages. We traced the observed errors from the affected page back to the generator code to identify three causes. First, the developer-lineage classifier tests calculation/formula keywords before comment typing, fails to recognize the leading \texttt{*} used for full-line comments in ABAP (an SAP programming language), and applies a generic SQL \texttt{AS} pattern that can select a \texttt{CAST} type instead of the final alias. This classifier explains the source-role manifestations. Figure~\ref{fig:sql-source-role} illustrates this error on the On-Spec Rate page. The first \texttt{AS} specifies the conversion type, \texttt{FLOAT}; the second names the output, \texttt{on\_spec\_percentage}. The generator selected the type as the alias. The page retained the source, yet described the wrong element as the output name.

\section{Detailed Case Analysis}
The earlier results counted documentation errors across all 28 pages. The next two cases explain what an individual error means for someone trying to understand a KPI. Yield shows how a correct-looking equation can omit a condition that changes the result. Gross Margin shows how a business formula and the program's calculation can disagree while the page still links to both. In each case, we show the intended calculation, the code, what the generated page says, and what the audit found.

\subsection{Ethylene Production Yield}
Production yield measures the output produced from a given amount of feedstock. In this archived example, producing 20 tons of ethylene from 100 tons of feedstock gives a 20\% yield. That familiar calculation applies when feedstock is positive. The actual program also specifies what happens when feedstock is zero or negative: it returns zero instead of evaluating the ratio. A reader needs that condition to understand why the software might report zero.

Listing~\ref{lst:yield-source} presents the Python function used in the experiment. It shows both the ratio and the return-zero condition.
\begin{lstlisting}[float=htbp,label={lst:yield-source},language=Python,breaklines=true,breakatwhitespace=true,caption={Verbatim Yield source excerpt from the unchanged study source; its file identity is recorded in the supplement.}]
def calculate_ethylene_yield_pct(ethylene_produced_tons: float, feedstock_input_tons: float) -> float:
    """Calculates ethylene production yield as a percentage of feedstock input."""
    if feedstock_input_tons <= 0:
        return 0.0
    return (ethylene_produced_tons / feedstock_input_tons) * 100.0
\end{lstlisting}
The generated page displays the positive-input ratio in its \emph{Formal Formula} field, the part of the page that presents the calculation as an equation. The saved study source, however, uses \texttt{feedstock\_\allowbreak{}input\_\allowbreak{}tons <= 0} and returns 0.0 on that branch. The reader-facing Logic Safeguards block omits this non-positive-input behavior. For the docstring shown in Listing~1, the generated lineage prose is ``Output alias: maps this expression to a in the result set.'' Direct source comparison identifies the statement as a function docstring, establishing the lineage-typing defect. The condition finding illustrates the criterion boundary exposed by independent review: two reviewers counted the visible source branch as disclosure, whereas one reviewer and the checker required the reader-facing safeguard layer to state the branch.

\subsection{Gross Margin Percentage}
\label{sec:gross-margin}
Gross margin is a business measure of how much revenue remains after paying the associated cost. In the archived KPI, the stated business formula and the program calculate different percentages from the same numbers. The example therefore tests whether the page makes the disagreement visible and whether its safeguard explanation refers to the correct calculation.

Let $R$ denote revenue and $C$ cost. The declared formula, $D$, divides the difference between revenue and cost by revenue; the implemented expression, $I$, divides revenue by cost. With revenue 200 and cost 100, the declared result is 50\%, while the program's expression gives 200\%. The two formulas retained in the dossier are
\[
D=100\frac{R-C}{R}, \qquad I=100\frac{R}{C}.
\]
For $R>0$ and $C>0$,
\[
\begin{aligned}
I-D &=100\left(\frac{R}{C}+\frac{C}{R}-1\right) \\
&=100\left(1+\frac{(R-C)^2}{RC}\right)\ge 100.
\end{aligned}
\]
Thus the implemented expression exceeds the declaration by at least 100 percentage points throughout the strictly positive domain, with equality in this lower bound when $R=C$. At positive revenue and zero cost, the declaration evaluates to 100 while the implementation guard returns zero; at zero revenue and positive cost, the declaration is undefined while the implementation returns zero.

The dossier correctly routes the explicit disagreement through \emph{Needs Review} and a Review Queue. Its safeguard text nevertheless describes a generic zero denominator even though the declared and executable representations use different denominators, and certification-oriented language appears alongside unresolved status. The page preserves explicit-conflict routing while also exhibiting a guard-binding discrepancy and certification wording beside an unresolved review state.

\section{Discussion}
\subsection{Interpretation of the Core Findings}
The Introduction asked whether a generated KPI page correctly explained the calculation it linked to. The Yield and Gross Margin cases showed why source access and explanation accuracy required separate checks: the code remained available while the page omitted a behavior-changing branch or lost the identity of the guarded denominator. Tracing those errors to the generator answered RQ1 by locating where the explanation went wrong. Recurring errors across archived outputs and alternative inputs were traced to shared generation rules; the changing guard outcomes showed that the same generator could describe some inputs correctly and others incompletely (RQ2).

The reviewer comparison separated agreement on an assessment criterion from the coverage of its automated rule (RQ3--RQ4). Source-role accuracy and condition disclosure received positive reviewer agreement, yet the source-role rule detected only two of 16 majority-reference failures. Agreement on what should be checked and success in detecting it were therefore distinct results. The other candidates required different treatment. Negative agreement led us to reject review-authority consistency. Negative agreement on commonly applicable disagreement cases led us to retain only the narrower marked-conflict routing check. Preserving a marked conflict and accurately explaining a calculation remained separately assessable properties.

\subsection{Relation to Prior Research}
The observed errors align with code--documentation consistency research. \citet{Xu2024} developed a method for detecting inconsistent code comments that addressed noise and labeling errors in training data. \citet{Zhou2017} compared API documentation with code to detect defects in parameter constraints and exception directives. The LEAP findings connect these concerns to generated KPI pages: the SQL example misdescribed a source element, while Yield omitted an implemented condition. Our study extended the comparison to business-facing formula, explanation, and safeguard fields, then traced errors to the generator. Separately assessing reviewer agreement and checker coverage exposed both ambiguity in the criterion and gaps in the implemented patterns.

Traceability and inconsistency-management research help explain what the retained evidence contributed. \citet{MaderGotel2012} studied maintenance of traceability links as software models changed; our audit examined explanations after the relevant source links were already present. The links made the disputed calculation inspectable. \citet{Nuseibeh2001} described retaining and managing known inconsistencies as part of software development. Gross Margin provided a concrete instance: both formulas and their review routing remained visible, making their disagreement available for inspection. The inaccurate safeguard on that same page showed why preserving a conflict and explaining the associated calculation are complementary responsibilities.

\subsection{Why the Checks Disagreed with Reviewers}
Figure~\ref{fig:sql-source-role} shows how a generator pattern produced a source-role error: a generic \texttt{AS} match selected the SQL conversion type instead of the final output alias. The checker targeted specified patterns of this kind and returned all expected control decisions. Cases C13 and C28 exposed a different gap: documentary comments were called KPI markers, whereas the checker targeted comments described as executable code and cast types described as aliases. Those cases explain how correct execution of prepared controls coexisted with low recall on reviewer-identified errors (Figure~\ref{fig:checker_results}a). They identify a missing class of role distinctions for subsequent rule development.

The condition result arose through a different mechanism (Figure~\ref{fig:checker_results}b). The checker flagged the same five pages under both comparisons. R1/R2 accepted source visibility as disclosure, whereas R3 required the written safeguard to state the condition and its variable. Consequently, the same three flags changed from unsupported to supported when the reference criterion changed, producing precision of 40\% and 100\%. The difference came from how disclosure was judged. For Yield, the disputed information was present in code but absent from safeguards; for Gross Margin, the safeguard lost the relationship between the guarded variable and the displayed denominator. These cases explain why an explicit disclosure definition is needed to interpret checker performance.

\subsection{Practical and Scientific Implications}
The worked cases provide concrete review questions. For Yield, a documentation maintainer should check that the explanation states the return-zero behavior for non-positive feedstock. For Gross Margin, the maintainer should identify the denominator being guarded and preserve both conflicting expressions and the review state. The source excerpt, generated description, and located discrepancy form a reviewable record connecting the business explanation to implementation evidence. Generator tracing then identifies the rule or template to inspect when the same error appears on several pages. This is a practical use of the evidence produced by the audit.

For subsequent checker development, the findings support two separate priorities: extend source-role patterns to the documentary distinctions illustrated by C13/C28, and specify the condition-disclosure criterion before collecting comparison judgments. A subsequent evaluation should test revised rules on additional codebases and retain separate measurements of reviewer agreement, rule conformance, and detection coverage. These measures address different questions about an audit. Comparative documentation studies and cross-role interpretation studies would then address correction effort, business readers' understanding, and joint review with developers as distinct outcomes.

\subsection{Study Limitations}
\label{sec:study-limitations}
The 28 pages came from one author-developed system; shared generation rules produced repeated errors, so page counts describe this output rather than independent generators. The earlier and alternative-input outputs extended the within-system comparison, and the four FastAPI tutorial examples established adapter execution. Broader recurrence requires evidence from other generators. The three-reviewer majority was a comparison reference, with overall $\kappa=0.446$, rather than a separately adjudicated final set. Reviewer disagreement therefore affects estimates measured against that reference. Original NA labels indicated inapplicability; restricting analysis to common applicability changed the case set and the disagreement estimate. The source-visibility and reader-facing criteria were identified in the returned judgments, so the R3 comparison measures agreement with the criterion implemented by the checker.

The fixed phase order and inclusion of both phase instructions in one packet prevented separation of checklist effects from familiarity or prior rubric access. The increase from 18/28 to 23/28 flagged pages was descriptive; all five additions arose from the rejected authority criterion. Root-cause inspection traced existing output to generator code; a prospective correction-and-retest evaluation remains future work. The routing check covered explicitly marked conflicts, and the condition rule covered comparisons with zero. Near-zero tolerances and function-domain cases require separate rules: real square roots require nonnegative inputs, logarithms positive inputs, and inverse sine/cosine inputs in $[-1,1]$; inverse tangent accepts all real inputs, and positive-base exponentiation allows negative exponents. The recorded outcomes concern documentation and checking. Human comprehension, correction time, and collaborative benefit require dedicated outcome studies.

\section{Conclusion}
We audited 28 source-linked KPI documentation pages and found descriptions that assigned source elements the wrong role or omitted conditions that changed the calculation. Comparing checker decisions with three reviewers' judgments showed which errors the implemented rules detected and missed. Inspection of the generator code traced repeated discrepancies to their causes. Reviewer agreement supported source-role accuracy and condition disclosure as the two retained assessment criteria.

The source-role checker achieved 12.5\% recall. On the same 10 eligible condition cases, precision was 40\% under source visibility and 100\% under reader-facing disclosure, with 100\% recall under both. The 100\% comparison measured agreement with the criterion the checker implemented. The broad disagreement criterion was narrowed to a separate check of explicit-conflict routing, which was preserved in 6/6 cases; negative reviewer agreement led us to reject the review-authority criterion. The initial majority issue set contained 18 of 28 pages.

The study contributed a source-grounded procedure for checking generated KPI explanations and an evaluation that distinguished reviewer support for assessment criteria from the coverage of automated rules. The worked cases located incorrect descriptions in their source evidence and traced repeated errors to generator logic. Subsequent evaluations can test revised checking rules on additional codebases using a disclosure criterion specified before reviewer assessment.
